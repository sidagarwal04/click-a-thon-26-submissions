0Executive summary

The event stream is well-formed at the top level — every session has exactly one VideoSessionStart and at least one heartbeat, and no exact-duplicate rows exist. However, deep inspection of the session lifecycle reveals 12 distinct anomalies / edge cases that will distort foreground-only concurrency if not handled. The most severe: the session_start_epoch column is 100% a sentinel value (2299-12-31), heartbeat cadence is far higher than the documented 1/min (with sub-second bursts), ~37% of heartbeat gaps exceed the 90 s timeout, and heartbeats continue while the app is backgrounded. The silver serving layer (sw_active_intervals, sw_delta_minute) is internally consistent (zero net delta, no inverted intervals), which is a good sign the derived model is sound — but the raw layer above it is noisy.

2Expected session workflow (from stories)

Per US-01/06/07/09 the canonical lifecycle is:

VideoSessionStart → VideoPlay → VideoHeartbeat* (≈1/min) → AppBackgrounded → AppForegrounded → VideoHeartbeat* → VideoSessionEnd
                          └── gap_timeout=90s: gap > 90s ⇒ active interval closes at last_hb + 90s (US-07)

Expected invariants: starts = ends, heartbeats ≈ 1 per minute, no events after VideoSessionEnd, no heartbeats while backgrounded, and each bg is followed by a fg (or vice-versa). Every deviation below violates one of these.

3Anomalies & edge cases

A1 · session_start_epoch is 100% sentinel garbage Critical

Every one of the 901,348 rows carries session_start_epoch = 2299-12-31 23:59:59.000 — the DateTime max sentinel. It cannot be used to derive a session start, so session boundaries must be computed from the VideoSessionStart event (or the min event timestamp) instead. This affects any logic keyed on session_start_epoch (US-01/08 session-aware path).

SELECT count() FROM ott_events WHERE session_start_epoch >= '2299-01-01' → 901,348 / 901,348

A2 · Heartbeat cadence far exceeds documented 1/min Critical

Heartbeats are documented as "every 1 minute" (US-07). Actual consecutive-heartbeat gaps (excluding exact-ms duplicates): 355,217 gaps < 60 s vs only 3,044 gaps ≈ 60 s. Sub-second spacing exists too: 1–100 ms (1,554), 101–500 ms (21,964), 501–1000 ms (27,322), 1–2 s (31,572), 2–5 s (38,136). The busiest session fired 1,792 heartbeats in 43 minutes (~0.7/sec).

Implication: a "heartbeat = alive" model using the documented 1-min cadence and 90 s timeout will massively over-split intervals and over-count active minutes. The 90 s timeout must be tuned to actual cadence, and per-event heartbeat payloads (see A5) must be understood first.

lagInFrame(event_timestamp) OVER (PARTITION BY video_session_id …) — heartbeat-only

A3 · 4 extra VideoSessionEnd events — duplicate/late ends Critical

VideoSessionEnd (10,870) outnumbers VideoSessionStart (10,866) by 4. Four sessions emit two end events (e.g. two ends 0.5 s apart). Applying a second end as another −1 delta would drive concurrency negative or double-count. Dedup rule (US-10) must key on (session, event_type, event) and ignore redundant second ends.

GROUP BY video_session_id HAVING countIf(event_type='VideoSessionEnd') > 1 → 4 sessions

A4 · 799 events arrive AFTER VideoSessionEnd Critical

Across 239 sessions, events appear after the session's end timestamp: 519 heartbeats, 239 AppBackgrounded, 28 AppForegrounded, 13 VideoPlay. These are out-of-order / late-arriving events (US-10) — if applied at arrival time instead of event time they would wrongly extend the session's active tail. Late events must land on their original event minute, and post-end events should be dropped (or flagged).

JOIN (max(event_timestamp) WHERE event_type='VideoSessionEnd') … WHERE event_timestamp > end → 799 rows

A5 · 366K "duplicate" heartbeat timestamps are actually distinct signal bursts High

158,986 distinct (session, type, timestamp) groups have count>1, totaling 366,083 extra rows at identical millisecond timestamps (up to 5 per ms). However these are not true duplicates: each carries a distinct event payload. Heartbeats carry 41 different signals — network-activity (176K), buffer-health (167K), video-resize (141K), BufferStart/BufferEnd, pause, resume, Seek, video_forward/rewind, dropped-frames, AdSkipTrueView, etc.

Implication: a dedup key of (session, event_type, timestamp) would throw away real state signals (US-10). These are bursts of telemetry sharing one ms stamp, likely batched by the player. They also inflate event volume ~40% — a naive per-minute count of heartbeat rows overstates active time.

GROUP BY video_session_id, event_type, event_timestamp HAVING count()>1 → 158,986 groups; re-check with event → 0 true duplicates

A6 · ~37% of heartbeat gaps exceed the 90 s timeout — every session is affected High

Of 841,756 consecutive heartbeat pairs, 16,305 gaps > 90 s (10,930 > 1 h) and they touch all 10,866 sessions (avg ≈ 1.5 per session). Gap histogram: ≤1s (69K), 1–60s (286K), 61–90s (1.9K), 91–180s (2.0K), 181s–10m (2.3K), 10m–1h (1.1K), >6h (10,876). The >6h bucket nearly equals the session count, so almost every session has at least one long silence.

Under the US-07 rule (close at last_hb + 90s) this splits virtually every session into multiple active intervals — consistent with the silver layer where 10,783/10,866 sessions have 2+ active intervals. This is the dominant edge case for concurrency correctness.

A7 · 4,733 heartbeats fire while the app is backgrounded High

Using a running counter over bg/fg events (+1 on background, −1 on foreground), 4,733 heartbeats arrive while the session is in backgrounded state. This directly contradicts the foreground-only assumption (US-06): "no heartbeat ⇒ not watching" is not reliable here, because the player keeps emitting heartbeats (network-activity, buffer-health, etc.) in the background.

Implication: heartbeat presence alone cannot mark active viewing — the bg/fg state machine must gate the active flag, and backgrounded intervals must contribute 0 regardless of heartbeats.

A8 · bg/fg imbalance & rapid toggling High

354 sessions have more backgrounds than foregrounds; 31 the reverse. Sequence analysis: bg→fg 14,247 · fg→bg 3,754 · bg→bg 25 · fg→fg 15. Real sessions show churn — e.g. a session toggling bg/fg five times in 6 seconds (10:52:35→10:52:41), and another with three fg/bg flips inside one second. AppBackgrounded/Foregrounded are documented as "not guaranteed events" (dataset_details) — an unpaired bg must be treated as an interval end, and an unpaired fg must still require a confirming heartbeat (US-06/07) to resume active state.

A9 · Content metadata gap — 142 titles missing video_type High

25,633 events / 250 sessions reference content whose video_type is empty (title & category present). Sample: 20972531 · "fuwiw kig" · video_type='' · category='bgfff'; the most active is 21007550 (1,612 events). These look like synthetic-filler rows and appear across the top traffic. video_type is a core serving dimension (US-04/11/12) — an empty bucket will silently absorb real concurrency unless coalesced to a fallback like 'unknown'.

0 unmapped content_id on join; 142 content_ids have empty video_type

A10 · Session duration extremes High

973 sessions (9%) last ≤ 1 minute (48 of them < 5 s, with VideoSessionEnd arriving before VideoPlay in some cases), while 12 sessions run > 6 hours and one spans 2 calendar days (07-25→07-26). Sub-minute sessions are likely abandoned starts / errors — they produce noisy +1/−1 deltas that can briefly spike or dip per-minute concurrency and should be reviewed (e.g. a 2.5 s session where VideoSessionEnd precedes VideoPlay breaks the ordering invariant).

G1 · Serving layer is internally consistent Healthy

silver.sw_delta_minute (19,448 rows): sum(delta) = 0, 9,717 negative vs 9,731 positive deltas — perfectly balanced. silver.sw_active_intervals (25,091 rows for 10,866 sessions): no inverted intervals, no zero-length intervals, `is_active` all 1. 10,783 sessions have 2+ intervals, matching the A6 heartbeat-split expectation. The derived model behaves as designed; the anomalies are upstream in raw events.

G2 · Core lifecycle is complete at session level Healthy

No session is missing VideoSessionStart, VideoPlay, or heartbeats; no session has multiple starts; no heartbeats occur before session start; there are no exact-duplicate rows; and all 3,357 content_ids resolve via LEFT JOIN (US-11). 293 VideoError events all belong to sessions that also ended cleanly.

5Recommendations

  1. Never trust session_start_epoch — derive session start from VideoSessionStart / min event timestamp (A1).
  2. Dedup on (session, event_type, event), not (session, event_type, timestamp), or 41 real heartbeat signals get lost (A5).
  3. Gate "active" on the bg/fg state machine; heartbeats emitted while backgrounded (A7) must not mark viewing.
  4. Recalibrate the heartbeat timeout from observed cadence instead of the documented 1-min/90-s defaults (A2, A6) — e.g. gap_timeout ≈ a few heartbeat periods.
  5. Handle post-end events: apply late events on their event minute and ignore anything after VideoSessionEnd (A4); ignore redundant second end events (A3).
  6. Coalesce empty video_type to 'unknown' at enrichment so US-04 filters stay complete (A9).
  7. Sanitize sub-minute sessions (A10) — a start that never plays is not an active viewer.
