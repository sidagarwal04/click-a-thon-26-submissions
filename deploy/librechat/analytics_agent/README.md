# Environment-only LibreChat analytics agent

This is the minimum runtime harness for the analytics portion of the Atlys
hackathon pipeline. LibreChat does the planning and review. ClickHouse does all
data aggregation and stores every durable artifact. Python only validates calls,
runs bounded aggregate queries, and computes a small set of statistical tests.

## Runtime setup

1. Build `Dockerfile`; it installs the fixed dependencies and copies the runner
   plus its private MCP adapter into `/opt/atlys`. Do not install packages during
   an agent run.
2. As an administrator, apply `ddl.sql` once. The runtime ClickHouse user only
   needs `SELECT` on approved source/catalog tables, exact `SELECT` on
   `agent.business_logic_embeddings_v1`, plus `SELECT` and `INSERT` on
   `atlys_agent.artifacts`; it does not need DDL or mutation privileges.
3. Configure these environment variables on `analytics-runner-mcp`:

   ```text
   CLICKHOUSE_HOST
   CLICKHOUSE_PORT=8443
   CLICKHOUSE_USER
   CLICKHOUSE_PASSWORD
   CLICKHOUSE_SECURE=true
   CLICKHOUSE_VERIFY=true
   ```

4. Provision Supervisor, Aggregate Analyst, and Evidence Reviewer with only the
   private `run_analytics` MCP tool. The MCP adapter converts each tool request to
   `ATLYS_REQUEST_B64`; agents never receive credentials or shell access. No
   filesystem MCP, custom tracing, or additional orchestration framework is used.

The only per-call runner input is `ATLYS_REQUEST_B64`; `server.py` creates it
inside the private service from the MCP `request` object and invokes the runner
without writing a file.

The runner emits exactly one JSON object. It never writes a local file. Full CSV
evidence remains in ClickHouse; an invocation exposes at most 20 records or a
50,000-character text chunk.

The first request therefore looks like:

```json
{
  "action": "bootstrap",
  "run_id": "UUID",
  "feature_slug": "unseen_feature",
  "instrumentation_handoff": {
    "status": "completed",
    "spec_md": "# Complete feature spec...",
    "event_tables": {"feature_shown": "default.inv_feature_events"},
    "tables": [{"name": "default.inv_feature_events", "description": "Raw events"}],
    "materialized_views": [],
    "aggregations": [],
    "decision_trace": []
  },
  "coverage_ledger": [
    {"question_id": "q1", "question": "...", "status": "pending"}
  ]
}
```

`coverage_ledger`, `run_id`, and `feature_slug` are generated by the Supervisor;
they are not additional Instrumentation Agent inputs.

## Analysis inputs

The analytics system accepts these substantive inputs:

1. the complete name-based instrumentation handoff, including the feature spec,
   event-to-table declarations, and qualified table/materialized-view names;
2. the current published business context from
   `agent.business_logic_embeddings_v1` plus the data/catalog already present in
   ClickHouse.

Bootstrap resolves exact DDL from live ClickHouse metadata; the Instrumentation
Agent never sends `CREATE TABLE` commands. The handoff is a resource declaration
that must be reconciled to live metadata;
multiple events may map to one unified raw table. Event mappings, relationships,
protected columns, deduplication keys, dimensions, units, source scopes, canonical
runs, and legacy mappings require live catalog, spec, business-context, and
bounded aggregate evidence. Ambiguous semantics become a context gap. Raw NDJSON
and event payloads are not analytics-agent inputs.

## Action contract

All actions require `run_id`; all except `bootstrap` also require that a context
snapshot already exists for that run.

- `bootstrap`: `feature_slug`, the complete `instrumentation_handoff`, and an
  optional precomputed `coverage_ledger` stored in the run manifest. Bootstrap
  validates and stores the handoff, confirms every declared object and non-empty
  raw event table, resolves live DDL and the table allowlist, then reads the latest
  current published context version from `agent.business_logic_embeddings_v1`
  before any artifact write.
  If context is larger than 50,000 characters, page the returned context artifact
  with `get_artifact`.
- `discover`: `feature_slug` and `tables`, an exact list of `database.table`
  values derived from the bootstrap catalog or business-context legacy references.
  Returns matching table definitions, columns/defaults/codecs/comments, sort/primary/
  partition/sample keys, sizes, and skipping indexes.
- `query`: `feature_slug`, `question_id`, `source_scope`, `sql`,
  `allowed_tables`, `protected_columns`, `expected_columns`,
  `table_scopes` (each table mapped to `feature` or `legacy`),
  `max_result_rows`, and optionally `boundary_columns`,
  `require_canonical_run`, and `canonical_run_id`.
  These safety fields are produced by the Aggregate Analyst from discovery; they
  are not Instrumentation Agent inputs.
- `stats`: `feature_slug`, `question_id`, `mode`, `input_artifact_ids`, and mode
  `options`. Modes are `rate`, `rate_compare`, `mean_compare`, `trend`,
  `anomaly`, `correlation`, and `adjust_pvalues`.
- `put_artifact`: persists a bounded `review`, `report`, or `context_gap` as JSON
  or Markdown.
- `get_artifact`: `artifact_id` plus `max_records <= 20`, or `offset` and
  `max_chars <= 50000` for text.
- `list_run`: lists metadata for the run without returning artifact contents.

`query` accepts one bounded aggregate `SELECT` or `WITH ... SELECT`: every
physical table must be fully qualified and allowlisted; the SQL must have a run
or time boundary, an aggregate, and a final `LIMIT <= 500`. Mutations, multiple
statements, `SELECT *`, raw-row output, and sampling/array aggregates are rejected.

## Analytics shapes

Keep calculations in ClickHouse and return sufficient statistics:

- funnel/rate/K-factor: distinct numerator and denominator counts by approved
  grain;
- distributions: count, mean, variance, and approved quantiles/histogram buckets;
- trends/anomalies/correlations: bounded time or segment buckets;
- comparisons: separate feature and legacy aggregates with aligned definitions;
- group/journey metrics: identities may exist inside a source-local inner query,
  but the outer result must immediately aggregate them away.

Before feature analysis, each declared raw-event type is represented by a
query-scoped normalized CTE view with a validated discriminator, common envelope,
event-specific attributes, and pushed-down time/run boundary. Every unordered
event-view pair receives best-effort relation analysis and a confidence score. No
persistent or temporary DDL is required.

The Aggregate Analyst persists one complete bounded JSON report referencing the
schema, SQL, aggregate, stats, bootstrap, and context artifacts. The Evidence
Reviewer persists one direct-answer review per PM question. After independent
review, the Supervisor returns validated PM-facing findings followed by compact
run/report/review audit IDs. No chart, insight-set, combination-matrix, or chunk
artifacts are part of the output model. Missing relations or incomparable baselines use
best-effort/insufficient-data results with reason codes and confidence, not
blocked analytical statuses or invented historical comparisons.

Derivation is conservative: handoff tables are feature scope; non-feature legacy
tables must be named by business context and independently discovered. Identifier-
like columns are protected from output unless business context explicitly defines
them as safe dimensions. Event mapping, deduplication, join keys, units and
boundaries require support from schema names/types/comments, the feature spec, or
business context. Aggregate profiling may confirm cardinality and coverage but
cannot establish semantic relationships by itself.

Per `agent-discovery-schema`, discovery precedes query generation. Per
`agent-query-safety`, the runner applies scan, byte, result, and execution limits.
Per `query-join-filter-before`, filter and aggregate each source before joining.

## Validation

The test suite exercises the transport, ClickHouse context loading, handoff
validation, SQL safety, bounded
previews, and every statistical mode. The following is a development check only;
the production image must already contain its dependencies:

```bash
uv run --with clickhouse-connect --with pandas --with scipy \
  --with statsmodels --with pytest \
  pytest deploy/librechat/analytics_agent/tests
```
